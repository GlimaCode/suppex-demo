# تست‌ها

```
php tests/run.php
```

یک دستور، همهٔ سوئیت‌ها، یک جمع‌بندی در انتها. خروجی غیرصفر یعنی چیزی شکسته.

برای اجرای فقط یک سوئیت، بخشی از نامش را بدهید:

```
php tests/run.php pricing
```

## پیش‌نیاز

دیتابیس محلی باید بالا باشد. با `SUPPEX-local\RUN-SUPPEX.bat` بالا می‌آید و روی
`127.0.0.1:3399` گوش می‌دهد. تست‌ها به دو دیتابیس دور‌ریختنی دست می‌زنند و
جدول‌ها را خالی و دوباره پر می‌کنند:

| دیتابیس | چه کسی | چرا |
|---|---|---|
| `suppex_test` | همهٔ سوئیت‌ها جز یکی | `tests/test-config.php` |
| `suppex_fresh` | فقط `test-migrate.php` | آن سوئیت دیتابیس را از صفر می‌سازد تا ثابت کند نصب تازه کار می‌کند؛ نباید به دیتابیسی که بقیه استفاده می‌کنند اشاره کند |

**هیچ‌کدام دیتابیس واقعی `suppex` را لمس نمی‌کنند.** ولی چون هر دو فایل پیکربندی
اسم دیتابیس را صریح می‌نویسند، قبل از اجرا روی یک ماشین جدید یک بار نگاهشان کنید.

سوئیت‌های `.mjs` به Node نیاز دارند. اگر Node نصب نباشد رد می‌شوند و در گزارش
گفته می‌شود — بقیه اجرا می‌شوند.

## ترتیب اهمیت دارد

سوئیت‌ها یک دیتابیس مشترک دارند و چند تایشان جدول‌ها را خالی و دوباره seed
می‌کنند. `run.php` آن‌ها را به همان ترتیبی اجرا می‌کند که روی هم بنا شده‌اند، و هر
کدام را در پروسهٔ جدا — چون اجرای همه در یک پروسه اجازه می‌دهد باقی‌ماندهٔ یک
سوئیت نتیجهٔ سوئیت بعدی را تعیین کند، که دقیقاً همان دسته باگی است که این تست‌ها
برای گرفتنش نوشته شده‌اند.

اجرای یک سوئیت به‌تنهایی ممکن است عدد متفاوتی بدهد، چون بعضی چک‌ها به کاتالوگی
که سوئیت قبلی گذاشته تکیه دارند. عددی که معتبر است، عددِ اجرای کامل است.

## این پوشه نباید روی هاست برود

`tests/.htaccess` دسترسی را می‌بندد، ولی بهترین کار این است که اصلاً آپلود نشود.
`tests/tmp/` هم موقتی است و در `.gitignore` هست.
